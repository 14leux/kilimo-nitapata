# Kilimo, Nitapata? v2, one-pager

Signed off in principle 2 Sep 2026 (Victor). Decisions from the interrogation are folded in below. Full specs follow in this folder once the messaging provider is chosen.

**In one line:** a two-sided release system where the sub-county agricultural officer opens a collection window and every registered farmer gets, on whatever phone they have, the same green/yellow/red status, the exact amount to pay, and what is still unsigned, so the counter is only collect, pay, leave.

**Problem:** today the farmer finds out at the counter whether he is served and what it costs, which is where overcharging and manipulation happen. Both sides need to see the same numbers before he travels, from the same rule table.

**Users**
- Officer (sub-county agricultural officer): holds the register, approvals, collection points. Opens the window, sees who is green/yellow/red and why, presses Release, sees who has not been reached.
- Farmer: receives the message, travels or does not, holds it up at the counter.
- Proxy: reads it for the farmer, relays it.
- Depot counter staff: not a user. The message has to survive them.

**v1 seed:** sample register, one officer screen, one farmer screen, one shared engine. Officer presses Release; each farmer's status is generated by `evaluate()` and delivered by in-app, SMS and USSD from that single result.

**Core flows (happy path)**
1. Officer opens the season window. Engine runs every farmer against their assigned collection point. Officer sees a board: green, yellow, red, with the blocking item per farmer.
2. Officer presses Release. Each farmer gets: collection point, verdict colour, bag price, subsidy covered, amount to pay, pending approvals with who signs, sources.
3. Farmer or proxy opens the message. Same status, same numbers. Travels on green, fixes the named item on yellow, does not travel on red.
4. An approval lands (chief signs). Officer marks it. Status flips. Both sides see it on next open; farmer gets a fresh message.

**Decisions locked (2 Sep)**
- Officer side is the sub-county agricultural officer, not depot counter staff. Counter staff never control the data.
- Small real backend: Vercel functions plus a key-value store. Release persists; the farmer side reads the same record from any device.
- Messaging: Twilio. WhatsApp sandbox is the primary push channel, SMS secondary (Kenya sender ID pre-registration means trial SMS can be filtered), USSD stays on the Africa's Talking sandbox because Twilio has no USSD. Decided 2 Sep after research, see tasks/ui-refresh-plan.md history in chat.
- Self-check stays. Release is the push, the existing check is the pull. Same engine.
- Cost lines are display only. No M-Pesa, no payment step. Data shaped so a pay step could be added later without changing the engine.

**In scope (v1):** officer board and release; farmer status with cost breakdown; delivery by in-app, SMS, WhatsApp (if the provider allows in the hour), USSD; a new gate, "subsidy released by government", set by the officer; approvals shown as named items with who signs; officer can mark an approval as signed.
**Explicitly NOT in v1:** payment; KIAMIS integration; live farmer records; accounts beyond a demo officer switch; marketplace; agronomic advice; multi-county admin.

**Stack at a glance:** same repo. `engine.js` gains cost lines (bag price, subsidy share, farmer pays) and the release gate. Officer and farmer are two modes of the same PWA. `api/` functions on Vercel for release, status read, approval update, and USSD. KV store for the register state. Messaging provider SDK called from the release function only.

**Open questions:** whether the subsidy share stays at the reported 40/60 split (source 4) or is parameterised per season; how a farmer is identified on the farmer side (phone number in the sample register, no login).
